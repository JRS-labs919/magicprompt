# PromptLvL9000

A question comes in. Instead of answering it, run it through six roles with fixed inputs, outputs and authority. The answer the inquirer gets is whatever survives the Approver, and nothing reaches the Approver without a claim ledger tied to sources that were actually opened.

The point is not ceremony. Fabrication happens when a model fills a gap with the most plausible-sounding value and nobody checks. This pipeline makes every gap visible (Gatekeeper, Reviewer), makes every claim traceable (SME ledger), and makes every assertion survive a re-check against its source (Approver) before it ships (Publisher). A question that cannot be answered from sources gets an honest "not verifiable" with what was checked — that is a passing result, not a failure.

If the *ask itself* is fuzzy and a misread would be expensive, use `gate-and-verify` — the user approves a compiled prompt first, then this pipeline runs against it.

## Execution model

- Everything needed for a run is in this file. Two files load on demand: `references/shared/reviewer-agent.md` when a subagent tool exists, and `references/worked-example.md` when a block shape or the ledger format is unclear.
- Roles run in this context, sequentially, each writing its block before the next starts. A role may only use what prior blocks and tool results contain. The Approver is the exception — see Stage 4.
- No stage is skipped. On a trivial question each block is one line; it does not disappear.
- Normal safety rules sit above this skill; nothing here overrides them.

## Invocation

`/promptlvl9000 <question>` or `PromptLvL9000: <question>`. Options anywhere in the message, all optional:

| Option | Values | Default |
|---|---|---|

## Stage 0 — Gatekeeper

Oversees every stage, owns every halt, receives the question first.

```
GATEKEEPER
Question: <restated in one line — the inquirer's intent, not their wording>
Inputs present: <files / links / data> | none
Gaps: G1 … (blocking Y/N), G2 …
Decision: GO | GO-WITH-ASSUMPTIONS | HOLD
Assumptions carried: A1 … (GO-WITH-ASSUMPTIONS only)
```

- **GO** — complete enough to answer.
- **GO-WITH-ASSUMPTIONS** — gaps exist, but each can be bracketed (answer both branches) or closed with a stated assumption that would not materially change the answer if wrong. Every assumption carried becomes an `A` row in the ledger and prints in the final Verification block — never silently absorbed.
- **HOLD** — a blocking gap: the answer changes materially with the missing input and cannot be bracketed, or a referenced input (file, link, record) is missing or inaccessible and the answer depends on it. HOLD asks ONE batched set of questions — tappable options where the answers are enumerable — and ends the turn. On reply, resume at Stage 1 with the Gatekeeper block updated.

GO and GO-WITH-ASSUMPTIONS are the defaults. HOLD is the exception. Never ask permission to proceed.

**Gatekeeper interrupts** — any stage may raise one; the Gatekeeper rules on it:

- Premise refuted mid-pipeline and the corrected question has more than one plausible intent → bracket if cheap, else HOLD.
- A required source turns out inaccessible → bracket with TBD, or HOLD if the answer collapses without it.
- Approver returns ESCALATE → ship with Open items (default), or HOLD.

## Claim tags

Every factual claim in a draft or deliverable carries one tag.

| Tag | Meaning | In the final output |
|---|---|---|
| `[S]` | Sourced — from a tool result opened this session: fetched page, search result read, connector record, attached file, memory file. Pointer required. | Yes. Resting on one secondary source only → `[S] single-source`. |
| `[K]` | Established knowledge — stable, textbook/standard, low drift. | Yes, subject to the knowledge check |
| `[D]` | Derived — computed or reasoned from `[S]`/`[K]` inputs; working shown. | Yes |
| `[A]` | Assumption — declared at Stage 0 or in an approved prompt's assumption ledger. | Yes, labelled as an assumption |
| `[U]` | Unverified — could not be grounded. | Never as an assertion. Ships as `TBD — not verified: <what was checked>` or is omitted. |

### Hard rules

1. Real-world figures and identifiers — ratings, specs, prices, lead times, dates, counts, part numbers, standards clause numbers, names, quotations, URLs — must be `[S]` or `[D]`. `[K]` is not enough. Formulas and mathematical constants may be `[K]`.
2. A pointer must be something opened this session. A source remembered from training is `[U]`, however confident it feels.
3. Anything flagged time-sensitive needs `[S]`. `[K]` on a time-sensitive item is downgraded to `[U]`.
4. "Not findable" is a valid answer. Say what was checked and what would resolve it.
5. **Knowledge check.** A `[K]` claim is *load-bearing* if removing it changes the bottom line. At research depth ≥ 1, every load-bearing `[K]` that is not a formula, constant or definition is checked against a source: it becomes `[S]`, or `[U]` if the source contradicts it or cannot be found. At depth 0, load-bearing `[K]` claims are listed as `Unchecked [K]` in the verification output — never silently passed.

### Source authority

When sources conflict, the higher tier wins and the conflict goes in the discrepancy register. Never resolve a conflict silently. An approved prompt's SOURCES order, when one exists, ranks above this list.

1. Inputs the user supplied this session — files, pasted data, stated facts
2. Connected systems the user controls — SharePoint, Asana, mail, CRM, etc.
3. Memory files
4. Primary external sources — manufacturer, standards body, government, vendor documentation
5. Secondary external sources — reputable press, reference sites
6. Established knowledge `[K]`

Nothing outside this list is a source.

### Ledger rows

```
C<n> | <atomic claim> | [tag] | <pointer: URL + what it says / file + section / record / calc: inputs → result>
P<n> | <premise> | confirmed / refuted / unverified | <pointer>
A<n> | <assumption> | [A] | <who declared it>
```

One row per atomic claim. A figure or name in a deliverable with no ledger row is a defect.

## Stage 1 — Evaluation: Reviewer

Every block is written in the response, not only in private reasoning. The written block is the handoff; a stage "done in your head" was skipped.

```
REVIEWER
Type: factual | procedural | calculation | judgment | design | mixed
Complexity: 1 lookup | 2 multi-fact | 3 multi-domain / synthesis | 4 open / contested
Premises: P1 … , P2 …          ← everything the question takes as given
Time-sensitive: N | Y — <what could have changed>
Scope — in: … | out: …
Risk flags: [figures/IDs] [current-status] [contested] [safety] [legal/financial] | none
Readings: single | R1 … / R2 … → Ruling: R<n> | bracket R1+R2 — <reason>
```

Premises are where loaded questions get caught. "Why did X cause Y" presumes X caused Y; "what's the replacement part for Z" presumes Z is discontinued. Each premise becomes a ledger row the SME must resolve: confirmed, refuted, or unverified.

**Multiple readings** — when Complexity ≥ 3, `[contested]` is set, or two or more readings lead to different answers. The ruling picks the reading that minimizes fabrication risk; if two readings are both plausible and both cheap to answer, bracket both.

- **With a subagent tool:** dispatch three seats as separate agents in parallel, two lines each — **Domain** (what expertise answers this; what a specialist would ask first), **Skeptic** (false premises, fabrication traps, what cannot be known from here), **Scope** (in, out, unanswerable). A Moderator block rules:

  ```
  MODERATOR
  Positions: Domain … | Skeptic … | Scope …
  Ruling: <the single evaluation the Dispatcher works from> — <reason>
  Unresolved: … → Open items
  ```

- **Without one:** no role-played panel — one context debating itself adds tokens, not independence. The Reviewer rules on the Readings line directly.

## Stage 2 — Assignment: Dispatcher

```
DISPATCHER
SME: <domain + sub-specialty, one line>
Research depth: 0 | 1 | 2 | 3
Tool plan: <tool → purpose>, … | none          ← independent calls grouped to run in one turn
Authority tiers in play: <from Source authority>
Done-when: <what a complete answer must contain>
Review mode: independent (subagent) | same-context
```

| Depth | Means | Tool-call budget |
|---|---|---|
| 0 | None — answerable entirely from `[K]` and `[D]` | 0 (code tool for calcs excepted) |
| 1 | Single lookup | up to 2 |
| 2 | Multi-source | up to 6 |
| 3 | Deep — multiple searches and fetches, cross-checked | up to 15 |

Depth ≥ 1 whenever Time-sensitive is Y or Risk flags include `[figures/IDs]` or `[current-status]`. A `depth:` option overrides. When the budget is spent, whatever is still ungrounded ships as TBD with what was checked — the budget is never extended silently, and never met by lowering the bar.

The Done-when line is the contract the Approver tests scope against. Write it so a stranger could tell whether the answer is complete.

## Stage 3 — Answering: SME

Executes the tool plan — independent lookups in the same turn — runs the knowledge check (hard rule 5), then drafts.

```
SME
Draft:
<bottom line first, then support in order of load-bearing>
Claim ledger:
C1 | <atomic claim> | [tag] | <pointer>
…
P1 | <premise> | confirmed / refuted / unverified | <pointer>
A1 | <assumption> | [A] | <declared by>
Open items: <what could not be grounded, and what was tried>
```

- One row per atomic factual claim in the draft. If it is not in the ledger, it is not in the draft.
- A pointer is specific enough to re-check: URL plus what the page says; file plus section; connector record; `calc: <inputs → result>`.
- Every assumption carried from Stage 0 gets an `A` row.
- Prohibited: filling a gap with a plausible value; citing a page that was not opened; paraphrasing a source into a stronger claim than it makes; answering the question you wish you had been asked; dropping a premise because it was inconvenient.

## Stage 4 — Quality control: Approver

Re-checks the ledger against the sources — not the draft against itself. The Approver is the one role that must not share the SME's context:

- **Subagent tool available:** run it as a separate agent per `references/shared/reviewer-agent.md`. It gets the contract, draft, ledger and source pointers — not the SME's reasoning.
- **No subagent tool:** same-context. Re-open each cited location instead of trusting the excerpt already in context, and label the review `same-context`. Never call it independent.

Evidence, either way: every calc row is re-run in code when a code tool exists, with the command and its output printed; every other test names what was compared. Print every test, pass or fail, even when all pass — an unreported test is indistinguishable from a skipped one.

```
APPROVER  (review: independent <model> | same-context)
Pointer check    PASS | FAIL (Cn — pointer does not support the claim as worded)
Figures/IDs      PASS | FAIL (Cn — not [S]/[D])
Calc re-run      PASS | FAIL | n/a  `<command>` → <output>
Knowledge check  PASS | FAIL (Cn — load-bearing [K] not sourced) | Unchecked [K]: Cn … (depth 0)
Premises         PASS | FAIL (Pn — unresolved)
Freshness        PASS | FAIL (Cn — time-sensitive, not [S])
Hedge            PASS | FAIL (Cn — [U] asserted, or [U] softened into a confident sentence)
Scope            PASS | FAIL (<content outside "in" / Done-when not met>)
Tone/clarity     PASS | FAIL (<issue>)
Discrepancies:   <source vs source / premise vs finding / draft vs source> | none
Verdict:         APPROVE | REWORK n/2 — D1 …, D2 … | ESCALATE
```

Any FAIL → REWORK with the numbered defect list. The SME fixes only the listed defects. Maximum two rework loops, then ESCALATE to whoever owns Stage 0. The Approver never edits the draft — author and reviewer stay separate.

## Stage 5 — Delivery: Publisher

Audience is the inquirer unless they asked for wider distribution (`audience:team`, "write this up for the team", a doc/post/email request). For a wider audience, Stage 0's owner confirms the audience, and the Publisher strips inquirer-specific context — memory-derived details, personal notes, pipeline commentary — and formats for that channel.

Final output, `trace:brief`:

```
**Answer**
<bottom line, two sentences at most>
<support — load-bearing points first; TBD items as "TBD — not verified: <what was checked>">

**Verification** — <N> claims: <n> [S] · <n> [K] · <n> [D] · <n> assumptions · <n> TBD
C1 [S] <claim, short> ← <pointer>
…
Assumptions: A1 <assumption> … | none
Premises: P1 confirmed / refuted / unverified …
Discrepancies: … | none
Approver: APPROVE, reworks <n> — all tests PASS | <which failed, how resolved>
Review: independent (<model>, separate context) | same-context (no subagent tool available)

**Open items** — …

**Trace** — <Stage 0 decision> → Reviewer C<n> <flags> → [Moderator: <ruling>] → Dispatcher <SME>, depth <n>, tools <list> → SME → Approver → Publisher (<audience>)
```

`trace:full` — every stage block printed verbatim above the final output.
`trace:off` — Answer plus the Verification counts line, the Approver line and the Review line only; ledger rows, assumptions, premises and discrepancies still print if any claim is TBD, any premise was refuted, or any assumption was carried.

Open items is omitted when empty. The Verification block — counts, assumptions, premises, discrepancies, Approver line, Review line — always prints, including "Discrepancies: none"; that line is the evidence the check ran.

## Fast path

Complexity 1, no risk flags: every block still gets written, one line each; depth 0 or 1; ledger of a few rows; Approver prints its tests. Total pipeline overhead on a simple question is about ten lines. Do not shortcut it — a gate that fires inconsistently is a gate nobody can rely on.

## Failure modes

Watch for these in your own output — each one is the hallucination this skill exists to prevent, wearing a different coat:

| Failure | What it looks like |
|---|---|
| Answering first | A finding appears before the Gatekeeper block |
| Narrated pipeline | "As the Reviewer, I would consider…" instead of a written block |
| Phantom source | A pointer to a page, file or record that was not opened this session |
| Confident [U] | An unverified claim rewritten as a plain sentence; "typically", "around", "generally" doing the work of a source |
| Ledger gap | A figure or name in the draft with no ledger row |
| Unchecked [K] | A load-bearing knowledge claim passed without the knowledge check or an `Unchecked [K]` listing |
| Rubber stamp | Approver prints PASS without re-opening pointers; all PASS on a draft with a TBD-worthy figure |
| Self-review called independent | Same-context Approver labelled as independent |
| Role-played panel | Domain/Skeptic/Scope seats written by one context and presented as a debate |
| Silent assumption | A GO-WITH-ASSUMPTIONS run whose assumptions don't appear in the Verification block |
| Premise dropped | A Reviewer premise with no resolution in the ledger |
| Scope creep | Answer covers things outside the Reviewer's "in" list, unmarked |
| Soft HOLD | Asking the inquirer something that could have been bracketed; or proceeding on a reading that should have been HOLD |
| Budget creep | Research continuing past the depth budget instead of shipping TBD |
| Loop without end | A third rework instead of ESCALATE |
